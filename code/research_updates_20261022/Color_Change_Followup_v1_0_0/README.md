# Color-change follow-up v1.0.0

Expected runtime: **30–90 minutes** on the existing MacBook/external SSD with 10 workers. A completed restart should take **5–15 minutes**. These are estimates, not measured laptop benchmarks. Slow external I/O or unusually slow fixed-effect convergence can take longer.

Put the ZIP in `$HOME/Desktop/Lichess_Desktop`, extract it, then run `bash Color_Change_Followup_v1_0_0/RUN_FOLLOWUP.command`. The launcher uses `/Volumes/XT_Pro/lichess_kindness/venv/bin/python`. It verifies the package, keeps the Mac awake, logs progress and prints the result ZIP path. It installs nothing. Dependencies are the existing NumPy, Pandas, PyArrow and DuckDB; no SciPy, Statsmodels, Numba or new environment is required.

This is the focused diagnostic/power-screen pass authorized after the completed first pass. It reads the existing ZSTD Parquets and stored opportunity states. The first-pass output root is `derived/replication_36m/color_change_firstpass_v100`. It does not rerun the rating history, Stockfish, API enrichment or account/identity recovery. It writes to a separate `derived/replication_36m/color_change_followup_v100` cache and `output/color_change_followup_v100` report root. Allow 20 GiB free and at least 16 GB RAM. Independent monthly tasks use up to ten processes with one DuckDB thread each; larger summaries use ten DuckDB threads; support scenarios run sequentially using memory-mapped arrays. API-frame diagnostics use at most three two-thread processes. These stages do not run concurrently with each other.

The package produces:

- Competitive and clearly losing dose distributions by exact information window, color, RD, and established/returning status. Premium changes include signed shifts, individual ratios, quantiles and ratios of mean magnitudes.
- Reconstruction errors in the actual opportunity/cohort/board cells, matched to November 1–18 pre-change cells. Draw integer distributions keep displayed ties separate. Calibration counts unobserved changes explicitly; it never replaces missing changes with zero.
- Returning-player sample counts, history coverage, observed-error calibration and November pre-period support. Older pre-period inactivity histories remain missing; the code does not manufacture them.
- Outcome-free residualized treatment support after chooser and week effects, d_G's main effect, color, old K/E, board evaluation, ply, clocks/missingness and speed. These are diagnostic controls, not the final A3 specification: account age and full time-control/stage detail are not available in the normalized cache. Two prespecified truncation scenarios end January 7 and January 30; neither declares a grace deployment date. Singular controls and convergence are reported.
- A pre-period weekly power screen for the unweighted White-minus-Black grant-rate contrast: 8 preceding weeks versus 4 or 8 later weeks; 10,000 moving-block draws at lengths 4 and 8, a 5% two-sided critical value and an 80%-power MDE. Twelve placebo dates are frozen in the code. This assumes stable historical time dependence and does not claim the finite-block screen is a causal confidence interval. It does not estimate A3/A4 MDEs or test an observed post-policy effect.
- January and, when available under the same modern contract, February/March candidate-frame entry diagnostics. It authenticates existing API completion checkpoints, reconciles active-resolution IDs to the prepared opportunity panel, separates missing clocks, separates kindness draws from other draws, normalizes `ultraBullet`, and withholds seven-day contrasts unless all fourteen days are present. It never uses a targeted candidate share as the platform-wide IV control.
- A bounded inventory of February's historical lineage plus a useful daily active-outcome table from its existing opportunities. Legacy paths are reported for review; schema similarity alone never makes a historical cache a certified denominator. No new API work is initiated.

The existing 41,534,331-row main-sample authority was recovered from the prior milestones package. Its rule is `source='pool' AND previous_classification_status='not_mutually_adjacent_observed'`; the certificate explicitly does not certify every literal immediate rematch. It covers November 2023–October 2025 only. The runner authenticates those existing monthly files and joins membership by game ID. Post-period membership remains unknown. Pool-only pre-period summaries are separate from the all-source series: do not combine them into a common-sample event study. Missing pool files do not trigger recovery or silently redefine the all-source sample.

The run retains the first pass's fixed established cohort: at least 100 same-speed rated updates by October 31, 2023. The strict returner additionally has RD ≥200 and at least 90 days since the preceding same-speed rated update. This supplies genuine earlier history, but is not a new account-age measure.

The anchored replay lacks fractional rating levels. Exact displayed-visibility shares and cumulative informative-feedback counts remain unidentified. Awareness scenarios in the power table are assumptions (5%, 10%, 20%, 50%, 100%). The illustrative smooth-profile prediction uses the previously stated 0.3–0.4 pp per 100-rating-point slope; it is not a newly estimated slope, an MDE, or the prediction for a symmetric threshold DDD.

No formal GO decision, behavioral DiD, threshold DDD, causal bound or IV estimate is released. That is the agreed order: review the calibration, support and power diagnostics, resolve sample/censoring dependencies, then freeze the estimable behavioral specifications. `POWER_GATE.json` and `GRACE_AND_IV_STATUS.json` distinguish those dependencies from computation failures.

Restart with the same command. Completed narrow monthly Parquets and completed support scenarios are verified and reused. Inputs, formulas or authority changes cause an explicit stop; existing files are preserved. No broad historical scan is launched to repair missing inputs. The result bundle contains aggregate results and code, not game/account-level Parquets.

Optional settings: `LICHESS_PROJECT_ROOT`, `LICHESS_TRANSFER_ROOT`, `LICHESS_COLOR_PYTHON`, `LICHESS_COLOR_WORKERS` (1–10), and `LICHESS_COLOR_MEMORY_GB` (DuckDB memory budget, default 8). DuckDB's budget is not a total RSS cap; Python and memory-mapped arrays add overhead.

Validation: tests exercise exact policy timestamps, keyed pool membership, actual-opportunity prediction parity, signed calibration, API-frame/clock reconciliation, full-window checks, iterative absorption against dense least squares, power calculation under simulated dependence and checkpoint reuse. A full run on the 53.6 million state-covered opportunities can only be verified on the project drive.
